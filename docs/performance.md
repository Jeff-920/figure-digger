# 后端性能与缓存

## 已落地的优化

- **分析配置缓存**：`analyze` 以 PDF 内容哈希、页码、DPI、需求、`find_series`、模型和 endpoint 为键，把 `config.json` + `panels/` + `figures/` 存到 `.analysis_cache/`。同一 PDF 同参数重跑会直接恢复配置，跳过选图、面板定位和轴识别。
- **图片预处理缓存**：`prepare_image` 以路径、mtime、大小缓存进程内最多 64 张已编码图片；同图多问题不重复解码/缩放/PNG 编码。
- **VLM 前缀缓存友好**：多模态内容块改为图片在前、问题在后，让同图不同问题尽可能共享系统提示 + 图片前缀。
- **批量并行**：新任务默认 `jobs=3`，并按 PDF 数量收敛；单 PDF 保持进程内执行以共享缓存。
- **历史页扫描**：跳过 `panels/`、`figures/`、`objects/`，并复用整任务扫描结果生成每篇文献状态。

## 缓存目录

- `.vlm_cache/`：VLM 响应精确缓存（图片 + 完整提示 + 参数）。删除可强制重新请求。
- `.analysis_cache/`：按 PDF/参数的分析配置缓存。删除可强制重新分析。
- `.vlm_log.jsonl`：逐次调用审计日志，包含 token 与上下文缓存命中数据。

## 实测参考

- 同一 PDF 的纯分析（无 VLM）：首次约 8.2s，缓存命中约 0.8s。
- `build_run_view()`：约 107–124ms → 13–21ms。
- 图片预处理：约 92–148ms → 缓存命中约 0.9ms。
- 现有 VLM 日志：本地精确缓存约 29%，DeepSeek 上下文缓存约 33%。

## 仍待做的更大改动

- 同一 PDF 内部的面板级并发：需要处理 API 限流、结果顺序、抽查一致性和模板写盘。
- 同图问题合并：能进一步减少调用次数，但会改变提示结构和校验语义。
- Files API 复用图片：减少重复上传体积，但不改变图片 token 计费，优先级低于前两项。
